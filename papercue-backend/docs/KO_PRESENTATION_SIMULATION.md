# 발표 지원 시뮬레이션 안내서 (한국어)

이 문서는 발표 중 발표자를 돕는 **adaptive prompting 프로토타입**을 설명합니다. 이 프로토타입은 더미데이터로 다음 흐름 전체를 실제로 실행합니다.

**발표 데이터 입력 → 실시간 맥락 해석 → 메모리·사용자 모델 갱신 → 지식 검색 → LLM Judge의 개입 판단 → 프롬프트 생성 → 모바일 전달 → 회복 추정·기록·평가**

기존 ‘청자 모델 기반 단서(cue)’ 기능은 그대로 두었습니다. 발표 시뮬레이션은 `app/presentation/` 아래의 별도 서브시스템입니다.

> 모든 발표 세션, 지식, 발표자는 **합성 더미데이터**입니다. 기본 Judge는 **규칙 기반 시뮬레이션(Mock)**이며, 실제 음성 인식·센서·LLM 출력이 아닙니다. 대시보드에는 이 사실이 항상 보라색 안내와 배지로 표시됩니다.

---

## 1. 빠르게 실행하기

```bash
cd papercue-backend
source .venv/bin/activate
python -m app.main                       # http://127.0.0.1:8000/dashboard/
```

- **발표 세션 개요:** `#/presentation` — 세션 목록, 세션별 지표, ‘자동 재생’·‘단계별 재생’ 버튼
- **발표 시뮬레이션 실험실:** `#/lab/<세션ID>`
  - `#/lab/<세션ID>/play` : 열자마자 자동 재생
  - `#/lab/<세션ID>/<단계>/<탭>` : 특정 시점을 바로 열기(예: `#/lab/S04_ko_too_fast/3/judge`)
- **발표 지원 평가:** `#/evaluation`
- **발표자 모바일 화면:** `#/mobile` — 새 탭(또는 같은 로컬 서버에 접속한 휴대폰 브라우저)에서 엽니다. 가장 최근에 조작한 실행의 상태를 0.5초마다 가져옵니다.

서버 없이 명령줄로 실행할 수도 있습니다.

```bash
python scripts/presentation_sim.py                                  # 전체 세션 요약
python scripts/presentation_sim.py --session S02_ko_missing_point --trace   # 단계별 판단 근거
python scripts/presentation_sim.py --out data/presentation_logs/batch       # JSONL + evaluation.json
```

## 2. Mock 모드와 실제 LLM 모드 전환

`.env`에서 설정합니다. 기본값은 모두 Mock이므로 API 키나 모델 없이 실행됩니다.

| 환경변수 | 값 | 의미 |
|---|---|---|
| `PRESENTATION_JUDGE_PROVIDER` | `mock`(기본) / `ollama` | 규칙 기반 Judge / 로컬 LLM Judge |
| `PRESENTATION_PROMPT_PROVIDER` | `template`(기본) / `ollama` | 템플릿 문구 / 로컬 LLM이 문구를 다듬음 |
| `PRESENTATION_RETRIEVER` | `keyword`(기본) / `embedding` | 키워드 검색 / 로컬 임베딩 검색(`EMBEDDING_PROVIDER` 사용) |
| `PRESENTATION_SEED` | 정수(기본 7) | 같은 시드와 설정이면 ID·판단·문구가 완전히 같습니다 |
| `PRESENTATION_JUDGE_NOISE` | 0~0.2(기본 0) | Mock Judge 효용에 시드 고정 잡음을 더해 판단의 민감도를 확인 |
| `PRESENTATION_WRITE_LOGS`, `PRESENTATION_LOG_DIR` | `true`, `./data/presentation_logs` | 끝난 실행을 JSONL로 저장 |

실험실 화면의 ‘시드·Judge·검색기’ 선택 후 **이 설정으로 새로 실행**을 누르면 환경변수를 바꾸지 않고 한 실행만 다른 설정으로 돌릴 수 있습니다.

**실제 LLM 모드(Ollama)**는 이 프로젝트의 원칙대로 이 컴퓨터의 Ollama만 사용합니다(원격 API 없음). `ollama serve`와 `ollama pull <OLLAMA_MODEL>`이 필요합니다.
- LLM Judge는 규칙 Judge와 **같은 관찰 정보와 결정론적 특징값**을 받아 구조화된 JSON으로 판단합니다.
- 코드가 LLM 출력의 ID(이벤트·메모리·지식)를 검증해 입력에 없던 ID를 지웁니다.
- **쿨다운·중복 억제 정책은 코드가 최종 적용**합니다. LLM이 쿨다운 중에 개입하겠다고 하면 억제로 바뀌고, 그 사실이 ‘정책에 의해 LLM 결정이 바뀜’으로 표시됩니다.
- LLM이 실패하거나 형식이 틀리면 규칙 기반 Judge로 자동 대체되고 ‘LLM 실패로 규칙 기반 Judge로 대체됨’ 배지가 붙습니다.
- 원격 API 키 기반 모델을 붙이려면 `generate_structured(task, payload, schema)`를 구현한 제공자를 `OllamaJudge`에 넘기면 됩니다. 다만 이 프로젝트는 로컬 전용 원칙을 따르므로 원격 제공자는 추가하지 않았습니다.

## 3. 더미데이터 구성

`sample_data/presentation/` (자세한 필드 설명은 같은 폴더의 `README.md`)

- **지식 베이스 2개:** 영어 논문 ‘GazeFlow’, 한국어 논문 ‘소리지도’(둘 다 가상). 핵심 주장, 연구 배경, 방법론, 주요 결과, 한계, 선행연구, 발표 원고, 슬라이드별 설명, 반드시 언급할 내용(필수 여부·짧은 단서·키워드), 예상 질문과 답변, 전문용어를 포함합니다.
- **가상 발표자 6명:** 언어, 숙련도, 평소 발화 속도(영어 wpm, 한국어 음절/분), 평소 군말 빈도, 선호 프롬프트 길이, 이전 발표 사건, 불확실한 성향 가설.
- **발표 세션 14개(이벤트 115개):**

| 세션 | 언어 | 상황 | 정답상 개입 |
|---|---|---|---|
| S01 | 영어 | 안정적인 발표 | 없음 |
| S02 | 한국어 | 실험 설계에서 기준선 설명 누락 | 슬라이드 전환 시 1회 |
| S03 | 영어 | 발화가 슬라이드 계획보다 느림 | 1회 |
| S04 | 한국어 | 빠른 진행 + 방법 핵심 생략 | 속도 1회, 쿨다운 중 억제, 누락 알림 1회 |
| S05 | 영어 | ‘basically’·군말 반복 | 1회(이후 작은 재발은 무시) |
| S06 | 한국어 | 짧은 침묵 후 8.5초 막힘 | 긴 침묵에서 1회 |
| S07 | 영어 | 전문용어로 청중 혼란 | 첫 신호는 대기, 지속되면 1회 |
| S08 | 한국어 | 질의응답에서 질문 오해 | 1회 |
| S09 | 영어 | 프롬프트가 도움이 된 경우 | 2회(둘 다 즉시 회복) |
| S10 | 한국어 | 의도적 멈춤·미룬 설명(개입하면 방해) | 없음 |
| S11 | 영어 | 한 번 지원한 뒤 추가 개입 억제 | 1회 |
| S12 | 한국어 | 후반부 시간 부족 | 시간 조절 1회, 마무리 유도 1회 |
| S13 | 영어 | 경계 사례: 장황한 질의응답 답변 | 1회(답변 구조 제안) |
| S14 | 한국어 | 경계 사례: 한 문장 뒤 스스로 보충 | 청중 혼란에서 1회 |

- **정답(ground truth)** 필드: `issue`, `expected_intervention`, `expected_prompt_type`, `expected_decision`, `expected_outcome`, `severity`, `target`, `note`. 로더가 이벤트에서 떼어 따로 보관하므로 Judge·메모리·사용자 모델·프롬프트 생성기에는 전달되지 않습니다(테스트로 확인). 대시보드에서는 ‘연구자 전용’ 배지와 함께만 보입니다.
- `previous_interventions`는 데이터에 쓰지 않고 엔진이 자기 상태에서 채웁니다. 시스템 행동을 데이터가 미리 정하지 않기 위함입니다.

## 4. 시스템 구조

| 단계 | 모듈 | 하는 일 |
|---|---|---|
| 입력 | `inputs.py`, `dataset.py` | 이벤트 공급. 실제 STT·슬라이드·청중·웨어러블 어댑터가 들어갈 자리(Protocol)만 정의 |
| A. Presentation Context | `context.py` | 필수 내용 언급 여부, 슬라이드 체류·계획 대비 지연, 남은 시간 대비 필요한 시간, 발화 속도(사용자 모델 대비), 군말·반복 표현, 침묵, 청중 반응, 질문-답변 일치를 매 이벤트 갱신. 문제(issue)를 ‘유형+대상’으로 유지하고 해결 규칙이 충족되면 닫음 |
| C. Memory | `memory.py` | 작업·일화·의미·개입·성찰 기억. 모든 항목에 생성 시점, 유형, 원본 근거, 중요도, 최신성, 신뢰도, 검색 점수·횟수, 관련 슬라이드, 생성 이유, 사용한 판단을 기록. 변경마다 이전/이후 값 저장 |
| B. Presenter User Model | `user_model.py` | 프로필 가설에서 시작해 관찰로 갱신. 속성마다 값·신뢰도·근거·변경 이력 |
| D. Knowledge / RAG | `knowledge.py` | 질의 생성, 조각별 점수와 구성, 판단에 실제 사용한 조각과 사용하지 않은 이유 |
| Judge | `judge.py` | 4가지 판단과 구조화된 근거 |
| 프롬프트 | `prompt_generator.py` | 한국어/영어 템플릿 후보 3개를 점수화해 선택, 대안과 선택되지 않은 이유 기록 |
| 결과 추정 | `outcome.py` | 이후 이벤트만으로 회복 여부 추정(발표자 입력 없음) |
| 엔진·평가 | `engine.py`, `evaluation.py`, `service.py` | 단계별 처리·시간 측정·오류 격리, 모바일 상태, 평가, JSONL 기록 |

### Judge가 개입 여부를 정하는 방식(Mock)

1. 활성 문제들을 `0.6×심각도 + 0.4×긴급도`로 정렬합니다. 이미 알린 문제는 ×0.6으로 낮춥니다.
2. 가장 높은 문제에 대해 효용을 계산합니다.

   `효용 = 0.28×심각도 + 0.22×긴급도 + 0.14×필수 내용 여부 + 0.10×지식 근거 강도 + 0.08×지속성 + 0.10×예상 효과 − 0.25×스스로 회복할 가능성 − 0.20×주의 분산 위험`

   각 항목에는 근거(이벤트·메모리·지식·사용자 모델 속성)가 연결되어 있어 대시보드에서 눌러 따라갈 수 있습니다.
3. 신뢰도 = `0.35×탐지 신뢰도 + 0.2×근거 이벤트 수 + 0.25×지식 근거 + 0.2×관련 사용자 모델 속성의 확신`
4. 최근 개입 정책: 직전 프롬프트의 쿨다운(짧은 문구 30초, 보통 40초, 초보자 −5초) 안이면 **억제**합니다. 단, 심각도 0.85 이상인 다른 종류의 문제는 예외입니다. 90초 안에 같은 문제를 이미 알렸다면 억제하되, 마무리 유도로 격상해야 하거나 이전 알림이 효과가 없었고 여전히 심각하면 다시 알립니다.
5. 효용 ≥ 0.36이고 신뢰도 ≥ 0.5이면 **즉시 개입**, 효용 ≥ 0.12이면 **대기·관찰**, 그 밖에는 **개입 안 함**입니다.

원시 chain-of-thought는 요청·저장·표시하지 않습니다. 대시보드의 ‘판단 요약’은 위 구조화된 값만으로 만든 한국어 문장이고, 영문 찬성·반대 근거는 ‘시스템 기록(영문)’으로 구분해 보여 줍니다.

## 5. 대시보드에서 추론 단계를 확인하는 방법

1. **발표 세션 개요**에서 세션을 고르고 ‘단계별 재생’을 누릅니다.
2. **재생 제어줄:** 처음으로 / 이전 단계(과거 시점 보기) / 재생·일시정지 / 다음 단계 / 끝까지 실행 / 재생 속도(1×~30×) / 특정 시점으로 이동(슬라이더) / 최신 단계 따라가기.
3. **이 시점의 처리 흐름** 8칸(이벤트 → 맥락 → 메모리 → 사용자 모델 → 지식 검색 → Judge → 프롬프트·모바일 → 결과 추정)에 선택한 시점의 요약이 나옵니다. 칸을 누르면 해당 패널로 이동합니다.
4. **판단 타임라인**은 슬라이드, 발화 이벤트, 감지된 문제, 메모리 변경, RAG 검색, Judge 판단(●개입 ◐대기 ○개입 안 함 ⊘억제), 개입·억제(■전달 □미전달), 개입 후 변화(✓ ~ ✗), 정답(연구자 전용)을 한 시간축에 겹칩니다. 열을 누르면 그 시점의 전체 상태로 바뀌고, 아직 실행하지 않은 열을 누르면 그 시점까지 실행합니다.
5. 탭별 확인 내용
   - **라이브 모니터:** 현재 슬라이드와 예상 내용(✓/○), 최근 발화, 남은 시간·지연, 발화 속도, 침묵, 군말·반복 표현, 청중 반응, 추정 긴장도·인지부하, 현재 문제, 모바일 표시, 최근 이벤트 스트림
   - **Judge 판단:** 최종 결정, 심각도·긴급도·신뢰도·효용, 판단 요약, 점수 구성표(값×가중치=기여, 근거 링크), 찬성·반대 근거, 관련 발화, 사용된 메모리·사용자 모델 속성·지식, 쿨다운 상태, 함께 검토한 문제 후보, 원시 신호, **정답과 비교**(오판이면 차이 설명)
   - **메모리:** 유형별 필터, 시점별 메모리 상태(중요도·최신성·신뢰도·검색 횟수·활성·사용한 판단·생성 이유), 이번 단계의 변경(이전 → 이후), 선택한 메모리의 변경 이력, 메모리 검색 점수, 단계별 연산 표
   - **사용자 모델:** 속성 표와 ‘왜 이 값인가?’(변경 이력, 갱신 규칙, 근거 링크), 값·신뢰도 변화 그래프, 발화 속도 추정치, 긴장도·인지부하, 개입 효과 추정
   - **지식 검색(RAG):** 질의와 질의 단어, 검색된 조각의 점수와 구성, 원본 문서, 현재 슬라이드와의 관계, 판단 사용 여부와 사용하지 않은 이유, 프롬프트 반영 여부와 채운 슬롯
   - **프롬프트:** 생성된 모든 프롬프트(억제되어 전달되지 않은 문구 포함), 우선순위·만료, 개인화 속성, 생성 근거, 대안 후보와 선택되지 않은 이유, 전달하지 않은 이유, 개입 후 관찰된 결과와 판정 규칙
   - **원본 이벤트·정답:** 관찰 이벤트의 모든 필드와 입력 출처, 연구자 전용 정답 라벨, 단계별 처리 시간과 오류
   - **평가:** 지금까지 재생한 이벤트의 정답 비교
6. 오른쪽 **모바일 화면 미리보기**는 그 시점에 발표자 휴대폰에 보였을 화면입니다. ‘모바일 화면 열기’를 누르면 실제 모바일 화면(`#/mobile`)이 새 탭으로 열리고 재생과 함께 바뀝니다. 모바일 화면에는 프롬프트, 중요도(색 띠 + 기호 + 글자), 사라지기까지 남은 시간만 표시되며 누를 버튼이 없습니다.

## 6. 평가 지표

‘발표 지원 평가’ 페이지와 `app/presentation/evaluation.py`에 같은 정의가 있습니다.

- 정답 양성 = `expected_intervention`이 참인 이벤트, 시스템 개입 = 실제로 전달된 프롬프트
- 정답 시각 t부터 t+20초 안에 전달된 프롬프트를 정탐으로 짝지음 → TP / FP / FN / TN
- 정밀도, 재현율, F1, 불필요한 끼어들기 비율(FP/전달 수), 중요 개입 누락 비율(심각도 high·critical 기준), 평균 판단 지연(초·이벤트), 개입 후 회복률((회복 + 0.5×부분 회복)/결과가 정해진 프롬프트), 프롬프트 유형 정확도, 4가지 판단 일치율, 이벤트 단위 정확도, 평균 신뢰도
- 언어별·시나리오별·프롬프트 유형별로 나눠 봅니다.

**현재 결과(기본 설정, 시드 7):** 정밀도 0.93, 재현율 0.93, F1 0.93, 4가지 판단 일치율 0.77, 회복률 0.97.
- S01~S12는 임계값을 정하면서 함께 작성했으므로 지표가 **낙관적**입니다.
- S13·S14는 임계값을 고정한 뒤 추가한 블라인드 점검용입니다. 여기서 FN 1건(S13: 답변에 기대 키워드가 들어 있어 장황한 답변을 놓침)과 FP 1건(S14: 사후적으로는 스스로 보충한 누락에 개입)이 나왔고, 임계값을 다시 맞추지 않고 그대로 두었습니다.

## 7. 향후 모델 학습을 위한 기록

끝난 실행은 `data/presentation_logs/<run_id>.jsonl`에 이벤트당 한 줄로 저장됩니다(실험실의 ‘기록 보기’, `GET /runs/{id}/export`와 같은 형식).
- `features`: 발화 속도 비율, 침묵, 군말(현재·창), 청중 집중·혼란, 각성도, 슬라이드 체류, 지연, 시간 예산 비율, 남은 시간, 활성 문제 유형, 인지부하·긴장도·반응성, 직전 프롬프트 이후 경과 시간
- `system`: 판단, 문제, 심각도·긴급도·신뢰도·효용, 프롬프트 유형, 전달 여부, 결과, Judge, 대체 처리 여부
- `labels`: 정답 라벨

이 형식은 개입 시점 예측기나 발표자 상태 분류기의 학습 데이터로 쓸 수 있습니다. `data/`는 Git에 올라가지 않습니다. 실제 참여자 데이터를 기록할 때는 기존 개인정보 규칙(`PRIVACY.md`)과 보관 기간 정리 절차를 함께 적용해야 합니다. 현재 발표 실행은 메모리에만 있고 SQLite 세션 삭제 기능과 연결되어 있지 않습니다.

## 8. 현재 한계

- 모든 입력이 합성 데이터이며, 임계값을 같은 데이터를 보며 정했기 때문에 성능 수치는 검증 결과가 아닙니다.
- 내용 언급 여부는 키워드 일치로 판단합니다. 바꿔 말하기나 부정문(“기준선은 생략하겠습니다”)을 구분하지 못합니다. S13처럼 키워드만 맞고 요점이 없는 답변도 놓칩니다.
- 사후적으로만 알 수 있는 ‘곧 스스로 보충할 것’은 예측하지 못합니다(S14).
- 질의응답의 기존 속도 문제가 질문 이벤트 동안에도 활성으로 남아 ‘대기·관찰’로 표시될 수 있습니다(S13_e02).
- 성찰 기억은 LLM이 아니라 고정 규칙으로 만듭니다. 메모리·사용자 모델의 설명 문장과 Judge 근거 문장은 영문 기록입니다(대시보드는 한국어 요약과 라벨을 함께 제공).
- 실행 상태는 서버 메모리에만 있어 서버를 다시 시작하면 사라집니다(같은 시드로 재실행하면 동일하게 재현됨).
- Ollama 모드는 가짜 로컬 HTTP 서버로만 검증했고, 실제 모델의 판단 품질은 평가하지 않았습니다.
- 모바일 화면은 실제 앱이 아닌 반응형 웹 페이지이고, 휴대폰에서 열려면 서버를 localhost 밖으로 노출해야 하는데 이는 기본적으로 막혀 있습니다(`PAPERCUE_ALLOW_NON_LOCAL_BIND`, 보안 검토 필요).

## 9. 실제 센서·발표 데이터로 바꿀 때 수정할 곳

| 대상 | 수정 위치 | 할 일 |
|---|---|---|
| 음성 인식 | `inputs.TranscriptSource` | 로컬 STT에서 발화 조각, 발화 속도(wpm/음절 수), 침묵 길이, 군말 수, 반복 표현 산출. 원음 저장 금지 |
| 슬라이드 진행 | `inputs.SlideTracker` | 발표 소프트웨어·리모컨 이벤트 연결 |
| 청중 반응 | `inputs.AudienceSignalSource` | 개인을 식별하지 않는 집계 집중도·혼란도. 동의·개인정보 검토 필수 |
| 발표자 상태 | `inputs.PresenterSignalSource` | 웨어러블 각성도(0~1)로 정규화 |
| 이벤트 조립 | 새 `EventSource` | 위 입력을 일정 주기로 `ObservedEvent`로 묶어 `SimulationRun`에 순서대로 공급(현재는 인덱스 기반 재생) |
| 탐지 임계값 | `context.DETECTOR_PARAMS` | 실제 신호 분포에 맞춰 보정 |
| Judge 가중치·기준 | `judge.WEIGHTS`, `T_INTERVENE`, 쿨다운 상수 | 수집한 기록(JSONL)으로 재추정하거나 학습 모델로 교체 |
| 지식 | `sample_data/presentation/knowledge` 형식 | 실제 논문·원고·예상 질문으로 작성, `PRESENTATION_RETRIEVER=embedding` 권장 |
| 모바일 전달 | `inputs.PromptDeliverer` | 인증된 휴대폰 연결(로컬 전용 원칙과 위협 모델 재검토 필요) |
| 데이터 보관 | `service._maybe_log` | 실제 데이터라면 SQLite 세션·보관 기간·삭제 절차와 연결 |
